# 交互式审批机制开源对照分析（packages_ai_agent / SiteClaw / LiteCrab）

## 1. 结论先行

三家对"危险工具执行前要不要人点头"给出了三种答案：

| | packages_ai_agent | SiteClaw | LiteCrab |
|---|---|---|---|
| **模型** | 零人工介入：纯静态策略 | 聊天式放行：LLM 转述 + 关键词应答 | 结构化审批协议：挂起 → 弹窗 → 显式决策 |
| 决策者 | 编译期/配置期规则 | 模型 + 自然语言关键词 | 用户（UI 按钮点击） |
| 一句话 | 机器全权决定，且存在多处 fail-open | 有审批的形，无审批的实——应答通道可被无关对话误触发 | 审批是显式、绑定、单次消费、限时、持久的状态机 |

核心结论：
1. **只有 LiteCrab 实现了严格意义上的安全权限审批**：显式指令（结构化 decision 字段）、动作绑定（编号+会话+参数摘要）、单次消费、超时自动拒绝、跨重启持久。
2. **SiteClaw 的时序漏洞从反面验证了本仓设计**：其自然语言放行不校验 yes 消息与审批请求的先后关系，历史中任何 yes 类消息都可放行最近的待审批命令——这正是本仓"自然语言永不放行"红线（第 11 步设计 §4.8）要堵的洞。
3. **两家各有一个值得记入 backlog 的设计点**：SiteClaw 的"硬拒绝不可审批底线"、小米的"输入侧注入模式检测"（见第 9 节）。

## 2. 对比口径与证据等级

- 全部结论以**代码为准**：file:line 均指向本地副本当前源码；两外项目的文档声称不作为依据。
- "死代码/断链"判定标准：全仓库 grep 无消费方/调用方，且给出搜索证据。
- LiteCrab 侧引用本仓已验证实现（30/30 CTest，含 31 项审批 E2E 断言）。

## 3. 三种模型总览

```text
packages_ai_agent（零人工介入）
  所有入口（CLI/飞书/微信/WS/MQTT/语音/cron/远程节点/A2A/MCP）
      → message_bus → agent_loop → tool_registry_execute
      → tool_guard_check（静态策略，同步返回允许/拒绝）
  无任何"等待用户"环节；系统提示词明示 "Use tools directly, no permission needed"

SiteClaw（聊天式放行）
  exec 命令风险 > Medium → 安全链软拒绝 "[approval_required]"
      → ReAct 循环退出，LLM 以文本向用户展示命令
      → 用户下一轮聊天回复（"是/同意/yes/ok/好的…"）
      → reactor 扫描对话历史关键词 → 提取命令 → 加入已批准集合 → 下轮放行

LiteCrab（结构化审批）
  非只读工具调用（解析成功后、执行前）
      → 挂起：审批条目（编号+会话+参数摘要+有效期）落盘，占位符写入上下文
      → 结构化 interrupt 响应 → UI 弹窗（允许 / 本会话总是允许 / 拒绝）
      → 新请求带 decision 字段 → 五连校验（编号/会话/未过期/未消费/摘要自洽）
      → 批准则执行并注入结果；拒绝则注入 rejected_by_operator；超时自动拒绝
```

## 4. packages_ai_agent：零人工介入

### 4.1 实际存在的四层静态策略

| 层 | 机制 | 位置 | 性质 |
|---|---|---|---|
| 工具开关 | `tool_enabled_<name>` 读 config.json | `tool_guard.c:199-204` | 死 API：写入接口 `tool_guard_set_enabled`（:250-259）全仓库零调用，只能手改文件 |
| 输入限长 | 32KB 硬编码 | `tool_guard.c:206-212` | 只看长度，不解析内容 |
| 敏感工具限流 | run_shell/write_file/edit_file 60s/10 次 | `tool_guard.c:39-45, 105-132` | 内存态，重启清零 |
| Shell 三级策略 | Kconfig 编译期：Allowlist(默认)/Full/Deny；白名单约 40 命令 + 黑名单 + 禁元字符 + 默认拒绝 | `tool_shell.c:39-176` | 仅 run_shell 有参数内容级判定 |
| 注入模式检测 | 12 条英文模式，命中拒整条消息 | `tool_guard.c:136-168` | 输入侧、LLM 之前；只能"阻止"不能"放行" |

工具执行唯一漏斗 `tool_registry_execute`（`tool_registry.c:532-573`）：guard 同步判定后直接执行，无人工介入点。

### 4.2 失败开放点（对照警示）

- 系统提示词明写 "Use tools directly, no permission needed"（`context_builder.c:116`）；SOS skill 明示"立即执行，不问确认"（`agent_skills/sos-alert.md:7`）。
- 入站 WS/A2A/MCP 端口 28789 **无认证**（`ws_server.c:363-391`），`tools/call` 直达工具漏斗。
- 出站 TLS `MBEDTLS_SSL_VERIFY_OPTIONAL`（`vela_tls.c:352` 等三处）——不验证书。
- 未知工具默认启用（`tool_guard.c:269-273`，"not configured → enabled"）。
- `install_skill <url>` 仅 HTTPS + 格式检查，无签名校验（`nsh_commands.c:735-797`）。

## 5. SiteClaw：聊天式放行

### 5.1 审批链路（五步）

1. **触发**：仅 `exec`（ShellCmd 类）命令风险 > Medium 阈值（阈值硬编码 `factory.rs:53-57`）。文件写/删除、`git push`、`npm install`、`web_fetch` 均**不触发**审批；`write`/`file_delete` 虽标 Medium+dangerous（`builtin.rs:141-154`）但生产安全链未注册 FileOps 守卫。
2. **软拒绝**：返回 `[approval_required]` 前缀错误（`security.rs:382-491`）；硬拒绝名单（rm -rf /、mkfs、sudo、`curl | bash` 等）则永久阻断、不可审批（:408-468）。
3. **挂起**：`ctx.approval_pending = true`（`tool_act.rs:484-490`），reactor 退出循环，审批信息写入消息 metadata（`runner.rs:402-406`）。
4. **呈现**：Gateway 把 metadata 转成纯文本 "[ApprovalRequired] risk=…\n<cmd>\nRespond with [approve] or [reject]"（`streaming.rs:160-188`）；TUI/WebUI 均为普通聊天文本。
5. **放行**：下一轮 `process_pending_approval`（`reactor.rs:750-786`）扫描对话历史：任一 user 消息命中关键词表（`reactor.rs:788-809`：是/同意/批准/确认/执行/yes/y/approve/ok/好的，含**前缀匹配**）+ 最近一条 `[approval_required]` → 提取命令 → `approve_command`（`state.rs:372-385`，trim 后精确匹配）。

### 5.2 四个结构性弱点

1. **自然语言可以放行**：任何以"是/yes/approve/ok"开头的句子均视为批准——本仓红线（第 11 步设计 §4.8）的反面实现。
2. **时序漏洞（越权面）**：关键词扫描是对话级存在性检查，**不校验 yes 消息出现在审批请求之后**（`reactor.rs:757-761`）。场景：轮 N 命令 A 被拦 → 轮 N+1 用户对无关问题回答"是的" → 轮 N+2 起命令 A 被静默放行——用户从未对该命令表态。
3. **无超时、无拒绝状态、无持久化**：不答则不了了之；`clear_approved_commands` 注释写了"超时清空"但**从未被调用**（`state.rs:387-390`）；批准集合与对话历史均内存（`assembler.rs:32-34`），重启全失效。
4. **提示语与实现不符**：提示让用户回复 `[approve]`，关键词表对带方括号写法**不匹配**（既不等于也不以裸词开头）——照提示原文回复反而无效。

### 5.3 两个亮点（值得借鉴）

1. **硬拒绝不可审批底线**：即使危险命令被塞进已批准集合，仍被永久阻断（`security.rs:457-468` + 单测 :788-808）——"用户批准"不是万能钥匙。
2. **命令风险分析**：多段命令（`;`/`&&`/`\n`）取最高风险、剥离 timeout/nice/sudo 等包装器再评估（`risk.rs:71-174`），防 `ls && rm -rf /` 与 `sudo rm` 式绕过。

### 5.4 死代码/断链清单（证明"设计对了但没接通"）

| 项 | 现状 |
|---|---|
| `ToolManifest.requires_approval` 字段 | 声明+设置，全仓库无任何读取/强制点（`executor.rs:123,160-163`） |
| WebUI 审批卡片（Once/Session/Always/Deny 四按钮） | 前端组件存在（`ApprovalCard.tsx:36-65`）、后端 `/approval/respond` 端点存在（`routes.py:1695-1730`），但 SSE `approval` 事件从不发出（`fanout.py:32-38` 只映射 observability/done/token 三种）、`choice` 无任何后端处理 |
| `clear_approved_commands` | 从未被调用 |
| WorkspaceGuard / DomainGuard / SandboxRouter | 已实现但未接入生产链（`factory.rs:59-61` 只注册 CommandRiskEvaluator）；沙箱后端不可用时**降级宿主执行**（`sandbox_router.rs:269-283`） |
| 安全链缺省 | 未设置 SecurityChain 时直接放行（`manager.rs:242-255`）——fail-open |

## 6. LiteCrab：结构化审批（本仓实现）

见 [step_10](../security/step_10_approval_store_design.md) / [step_11](../security/step_11_approval_agent_integration_design.md) 设计文档与实现。要点：

- **触发**：所有 `readonly == 0` 且启用且未排除（默认排除 memory_remember）且未获会话白名单且非告警来源的工具调用；判定收敛于单一函数 `approval_gate`（Step 7 Policy Engine 的替换点）。
- **挂起**：非阻塞两段式——占位符工具结果写入上下文并落盘，请求以结构化 `interrupt` 信封正常结束（Agent 线程释放）。
- **决策**：`decision` 字段（approve/reject/always_allow）+ `replyToInterruptId` 成对出现，是唯一放行通道；自然语言只得到引导响应（E2E 用例 6 守护）。
- **校验**：五连 fail-closed——编号存在 / 会话匹配 / 未过期 / 未消费 / 参数摘要自洽；审批单次消费（CONSUMED 终态）。
- **超时**：`timeout_ms`（默认 10 分钟，配置校验 10000-3600000）到期自动按拒绝处理（fail-closed），惰性解锁不占后台线程。
- **持久化**：仅 WAITING 条目落盘 `pending.json`（原子写 + 0600 + 容量 16 + 损坏整文件作废）；重启后 pending 可继续决策；会话白名单刻意仅内存（"没答完的问题要留住，已给的特权不跨重启"）。

## 7. 逐项对照表

| 维度 | packages_ai_agent | SiteClaw | LiteCrab |
|---|---|---|---|
| 审批触发 | 无 | 仅 exec 高风险命令（阈值硬编码 Medium） | 所有非只读工具（可配置排除清单） |
| 决策通道 | 无 | 聊天关键词（自然语言） | 结构化 decision 字段 + UI 按钮 |
| 自然语言 | 能触发工具（A2A 通道把 skill_id 合成为 "Call tool X" 注入，`a2a_handler.c:182-202`） | **能放行**（含前缀匹配与时序漏洞） | **永不放行**（引导响应 + E2E 守护） |
| 授权绑定 | 不适用 | 命令字符串 trim 后精确匹配 | 编号+会话+参数摘要（argsHash） |
| 防重放/偷换 | 不适用 | 命令 B 不被 A 的批准放行（做对了）；但 yes 扫描不校验时序 | 编号单次消费；摘要自洽校验 |
| 超时语义 | 无审批概念 | 无（清空函数是死代码） | 超时自动拒绝（fail-closed） |
| 重启持久化 | 限流状态清零；tool_enabled_ 文件持久但只能"禁用" | 批准与历史全内存，重启失效 | pending 审批持久化可恢复；白名单刻意不持久 |
| 会话维度 | 无会话概念，一切全局 | 会话级（每轮从历史重推导，事实上的"会话内同命令永久免批"） | 显式 always_allow 会话白名单，仅内存 |
| 不可审批底线 | Shell 黑名单（Allowlist 模式默认拒绝） | 硬拒绝名单，批准也不可绕过 | 暂无（见第 9 节 backlog #1） |
| fail 方向 | 混合偏 open（无认证入口/TLS 不验/未知工具默认启用） | 混合（风险 fail-closed；安全链未设=放行、沙箱降级宿主） | 全链 fail-closed |
| 风险分级 | SENSITIVE/MODERATE 两级（仅用于限流） | Low/Medium/High 三级 + 命令内容分析 | readonly 二值（riskLevel 字段闲置，待 Step 7） |

## 8. 对照验证的设计决策

| 观察到的反面案例 | 验证的本仓设计决策 |
|---|---|
| SiteClaw 时序漏洞：历史 yes 消息可放行最近待审批命令 | 自然语言红线（step_11 §4.8）：decision 字段是唯一入口 |
| SiteClaw 无超时、无拒绝状态：审批不了了之，历史中永久残留可被后续误触 | 超时自动拒绝 + 占位符惰性落地（EXPIRED 终态，上下文收口） |
| SiteClaw WebUI 审批卡片四按钮是死代码：设计了没接通 | 本仓 UI 卡片与协议同分支落地，31 项 E2E 全绿后才提交 |
| 小米 fail-open 系（无认证入口直达工具、TLS 不验、未知工具默认启用） | fail-closed 全链（Step 2 loopback 默认、审批存储不可用即拒绝执行） |
| SiteClaw 安全链未设置=放行 | 审批门与存储就绪检查绑定（`CrabApprovalIsReady`），未初始化即门闭 |

## 9. 借鉴点与候选 backlog

按价值排序，均对齐安全计划既有步骤编号：

1. **硬拒绝层（不可审批底线）**——来源 SiteClaw。即使审批通过也绝不执行的终极黑名单（如 exec_program 参数命中危险模式时直接拒绝，弹窗都省略）。落点：Step 7 Policy Engine 的 DENY 态规则素材。
2. **风险分级触发**——来源 SiteClaw。readonly 二值判定偏粗；Low/Medium/High + 参数内容分析（多段取最高、剥包装器）更精细。落点：Step 7；ToolSpec 闲置的 `riskLevel` 字段正是为此预留。
3. **输入侧注入模式检测**——来源小米。12 条模式虽原始，但它是三家中唯一做了输入侧防御的。落点：蓝图增强项 5.1 Guardrails。
4. **敏感工具无状态限流**——来源小米。滑动窗口仅数十行内存数组。落点：等 Step 6 Principal 建立后的按身份限流（计划 §378 已有此约束）。
5. **日志脱敏**——来源小米（6 类敏感字段 REDACTED，`tool_guard.c:284-320`）。本仓已知欠账，即计划 Step 3 未完成部分。

**明确不借鉴**：SiteClaw 的自然语言放行与时序弱绑定；两家的 fail-open 模式（安全链缺省放行、沙箱降级宿主执行、TLS 不验证书）。
