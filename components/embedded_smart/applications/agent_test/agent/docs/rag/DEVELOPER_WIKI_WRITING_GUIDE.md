# 开发人员问题诊断 Wiki 编写指南

## 1. 这份指南解决什么问题

开发 Wiki 是知识库的原始材料，不需要直接写成 `PLC_Diagnosis` 那样的完整 Skill，也不需要描述所有自动化状态机、工具协议和异常分支。

开发人员需要做的是：把一次问题定位和修复过程中最关键、最难从上下文推断的事实记录准确。后续由转换 Skill 完成问题归类、内容重组、步骤标准化、知识去重和知识库格式生成。

两者的职责区别如下：

| 开发 Wiki 负责记录 | 转换 Skill 负责生成 |
|---|---|
| 现场发生了什么 | 统一的问题分类 |
| 在什么设备和版本发生 | 问题标签和检索关键词 |
| 看到了哪些日志、告警和指标 | 结构化识别条件 |
| 最终确认的根因是什么 | 根因分支和优先级 |
| 实际执行了什么修复 | 标准诊断/修复流程 |
| 修改了哪个对象、什么值 | 工具调用所需的参数说明 |
| 怎样确认修改生效 | 参数验证步骤 |
| 怎样确认问题恢复 | 闭环验证步骤 |
| 哪些情况下不能使用该方案 | 停止条件和安全约束 |
| 来源案例、DTS、版本 | 引用和追溯信息 |

开发 Wiki 不需要写成程序，也不需要提前设计：

- problem/cause/flow/step ID
- YAML 数据契约
- Skill 路由表
- 完整状态机
- capability registry
- JSON 返回字段
- 自动化测试用例
- 所有可能的成功/失败分支

但是，下文标记为“必须记录”的事实不能省略。转换 Skill 可以整理事实，不能发明事实。

## 2. 最核心的写作原则

### 2.1 写事实，不只写结论

不推荐：

```text
通信异常是频段问题，调整频段后恢复。
```

推荐：

```text
问题发生时设备工作在Band 1。将目标CCO调整到Band 2，接口写入值为3，
读回仍为Band 2；之后连续6分钟查询未再出现目标通信异常告警。
```

### 2.2 写实际做过的动作，不把建议写成事实

需要区分：

- **本次实际执行**：现场真正做过，并有结果。
- **已验证通用方法**：在多个版本或案例验证过。
- **建议尝试**：尚未在本次问题验证。
- **推测**：目前证据不足。

不要把“可以尝试升级”写成“解决方法是升级”，除非已经明确目标版本并验证问题恢复。

### 2.3 精确记录变化对象

必须写清楚：

```text
修改哪个设备
修改哪个参数
修改前是什么
修改后是什么
通过什么入口修改
是否需要重启、重新组网或等待生效
```

尤其要区分：

- 告警上报设备
- 故障设备
- 参数配置设备
- 关联设备

这些设备可能不是同一个对象。

### 2.4 记录“如何知道成功”

至少分成两层：

1. **动作生效**：参数、版本、配置或文件确实发生了预期变化。
2. **问题恢复**：原来的告警、日志异常或业务现象确实消失或达到指标。

“命令返回成功”通常只能证明请求被接受，不能自动证明参数生效，更不能证明问题解决。

### 2.5 不确定内容必须明确标注

推荐用词：

```text
已确认
高度怀疑
可能相关
尚未确认
本次未验证
仅适用于某版本
```

不要为了让 Wiki 看起来完整而省略不确定性。

## 3. 一篇 Wiki 应该描述多大范围

推荐一篇 Wiki 描述以下任意一种内容：

1. 一次已经完成定位的典型问题案例；
2. 一个明确的故障机理及其处理方法；
3. 某个版本缺陷及其规避/修复方法；
4. 一个已经验证的诊断方法；
5. 一个具体参数或配置问题。

不推荐把“所有 PLC 通信问题”全部写在同一篇 Wiki 中。范围太大时，根因、适用版本和修复动作容易互相混淆。

如果一次现场问题包含多个独立根因，可以：

- 主 Wiki 记录完整案例；
- 每个可复用根因再单独形成短 Wiki；
- 或在文中明确区分“已确认根因”和“排查过但排除的原因”。

## 4. 必须记录的七类信息

### 4.1 问题现场和适用范围

必须记录：

- 产品、设备类型或板卡类型；
- 软件/固件版本；
- 站点或拓扑特征，如单 CCO、双分裂、内外置 CCO；
- 问题影响的对象和范围；
- 问题发生前是否做过升级、重启、导入配置、换板等操作。

如果版本不知道，明确写“版本未获取”，不要省略。

示例：

```text
设备：SD5091数采 + 内置MBUS
软件版本：Vxxx
拓扑：双分裂箱变，内置CCO和外置CCO各带一个子阵
影响范围：外置CCO下全部逆变器通信质量下降
问题前操作：前一天重新导入过白名单
```

### 4.2 问题现象

必须记录用户或系统实际观察到的现象：

- 告警名称、告警 ID、设备对象；
- 日志文件、关键词和代表性日志；
- 指标名称、实际值、正常值或判断阈值；
- 是否持续、间歇发生或可稳定复现；
- 首次发生时间和持续时间；
- 哪些业务正常、哪些业务异常。

不推荐：

```text
设备通信不好。
```

推荐：

```text
logger_run_log.log中fail_addr持续增加，5分钟内从120增加到486；
同时外置CCO下8台逆变器有6台间歇离线，但ASP没有产生对应活动告警。
```

日志只截取能说明问题的关键行，并隐去密码、Token、Cookie、个人信息和不必要的站点敏感信息。

### 4.3 定位证据和排除过程

记录最终根因是怎样被确认的，而不只是列出所有可能原因。

建议写：

- 查了什么；
- 看到了什么；
- 这个结果支持或排除了什么；
- 为什么进入下一步。

示例：

| 检查项 | 观察结果 | 判断 |
|---|---|---|
| 物理接线 | 相序和接地正常 | 暂时排除接线问题 |
| 当前频段 | CCO为Band 1 | 记录当前配置 |
| 同站点其他CCO | Band 2下通信正常 | 支持频段相关判断 |
| 切换Band 2后 | 丢包率由18%降到2% | 确认频段不匹配为本次主要根因 |

不需要把每次无意义的尝试都写进去，但关键排除证据不能省略。

### 4.4 根因结论

根因部分至少回答：

1. 最终确认的根因是什么；
2. 根因影响问题的机理是什么；
3. 根因是如何确认的；
4. 适用于哪些版本和场景；
5. 是否可能还有其他未排除因素。

推荐格式：

```text
已确认根因：
外置CCO当前频段不适合该子阵现场信道环境，导致通信丢包升高。

确认依据：
切换前Band 1下丢包率18%；切换Band 2并读回成功后，
相同测试对象和测试参数下丢包率降至2%，且通信异常告警消失。

适用范围：
本结论仅针对本次站点和当前硬件/软件版本，不代表Band 2适用于所有站点。
```

如果只是推测：

```text
疑似根因：……
当前缺少……证据，尚未确认。
本次未执行自动修改。
```

### 4.5 实际修复动作

这是后续转换成可执行知识库最重要的部分。

每个实际修复动作必须写清：

| 内容 | 需要记录什么 |
|---|---|
| 操作对象 | 具体设备、模块、通道或配置对象 |
| 操作入口 | 命令、API、WEB路径、APP路径或人工操作位置 |
| 输入参数 | 参数名称和值，值从哪里取得 |
| 修改前 | 原配置、版本或状态 |
| 修改后 | 目标配置、版本或状态 |
| 附加动作 | 是否重启、重新搜索网络、刷新配置 |
| 生效等待 | 需要等待多久及原因 |
| 风险 | 是否会断链、重启、清空配置或影响业务 |
| 权限 | 是否需要管理员、现场确认或变更审批 |

不推荐：

```text
调整频段，重新组网。
```

推荐：

```text
操作对象：外置CCO，不是告警上报的Logger对象。
入口：数采WEB > 设备监控 > MBUS(COMX-249) > 组网配置 > 网络频段。
修改前：Band 1。
修改后：Band 2；接口值为3。
附加动作：修改完成后执行“重新搜索网络”。
等待：等待约10分钟，使组网和通信指标稳定。
风险：重新搜索期间逆变器会短时离线。
```

### 命令/API 动作

如果使用命令或 API，记录：

- 完整命令或接口名称；
- 参数含义；
- 示例参数；
- 正常输出中的关键字段；
- 常见失败输出；
- 是否存在“返回成功但实际未生效”的情况；
- 如何读回确认。

### WEB/APP 动作

记录完整路径，不只写“在WEB上配置”：

```text
设备监控 > MBUS-inside > 组网配置 > 防串扰 > 使能
```

如果不同版本菜单路径不同，分别记录版本和路径。

### 升级动作

不能只写“升级到最新版本”，需要记录：

- 问题版本；
- 首个修复版本或推荐目标版本；
- 升级包/版本来源；
- 是否跨版本升级；
- 升级后需要恢复的配置；
- 升级后的验证方法。

### 人工或物理动作

记录清单和需要反馈的结果：

```text
检查箱变低压侧开关是否闭合；
检查ABC相线序；
检查通信柜空开；
反馈每项“正常/异常”并附现场照片。
```

### 4.6 验证结果

必须分别记录“动作生效验证”和“问题恢复验证”。

### 动作生效验证

示例：

```text
频段写入后重新读取信号8201，返回值为3，对应Band 2。
因此确认参数已经生效。
```

### 问题恢复验证

必须说明：

- 使用什么数据源验证：告警、日志、指标或用户业务；
- 验证的是哪个对象和范围；
- 等待多久；
- 检查几次；
- 成功阈值；
- 实际结果。

示例：

```text
修改完成后等待组网稳定10分钟。
对同一STA使用相同参数测试100包，OkRate由82%提升到98%。
随后每60秒查询一次目标通信异常告警，连续6次未再出现。
本次判定问题恢复。
```

如果是日志问题：

```text
以修改完成时间为检查点，只统计检查点后的新日志。
连续3个60秒窗口内fail_addr增量均不超过2；
日志采集正常，没有发生文件停止更新。
本次判定日志异常恢复。
```

不能写：

```text
修改后没有再看到日志，所以问题恢复。
```

日志没有更新可能表示采集停止，应标记为结果未知。

### 4.7 限制、失败处理和回滚

至少记录：

- 哪些情况下不要使用本方案；
- 本次是否尝试过失败动作；
- 修改失败或无效时做什么；
- 能否回滚；
- 回滚到什么值；
- 什么情况下必须停止并找人工/研发；
- 哪些结论只适用于本次站点。

示例：

```text
当前频段无法读回时不要继续自动修改。
写入响应不明确时先重新查询当前频段，不要重复执行写入。
切换频段后通信进一步恶化，可回到修改前Band。
如果所有支持频段均无改善，停止频段调整，转物理链路和信噪比排查。
```

如果没有经过验证的回滚方案，直接写“无已验证自动回滚方案”。

## 5. 建议记录但不是必填的信息

以下信息有助于后续知识优化：

- DTS、CSR、问题单编号；
- 来源文档及页码；
- 修复提交或版本说明；
- 现场拓扑图；
- 脱敏日志附件；
- 修改前后截图；
- 类似案例链接；
- 已排除但容易误判的根因；
- 常见错误操作；
- 后续预防措施；
- 谁可以确认或审批高风险动作。

这些内容可以帮助转换 Skill 合并重复知识、标注适用范围和生成引用。

## 6. 不需要开发人员写的内容

为了保持 Wiki 简洁，以下内容交给转换 Skill 和知识库维护流程：

- 统一问题编号和根因编号；
- 将自然语言归一为知识库章节；
- 将步骤拆成 Skill 所需的状态机；
- 给步骤生成内部 ID；
- 生成 Agent 路由词；
- 合并相似问题；
- 生成工具调用 JSON；
- 生成标准总结格式；
- 生成自动化测试骨架；
- 生成知识库索引；
- 根据告警、日志和人工来源生成不同验证器结构。

前提是 Wiki 已提供必要事实。转换 Skill 不应补造缺失的版本、参数、阈值和操作路径。

## 8. 完整示例

> 以下内容用于展示填写粒度，设备、版本和数值为示例。正式 Wiki 必须替换成真实现场数据。

# 频段不匹配导致 PLC 通信异常

## 1. 基本信息

| 项目 | 内容 |
|---|---|
| 产品/设备 | SD5091数采，外置CCO |
| 软件/固件版本 | V100R001C00SPCxxx |
| 站点/拓扑 | 双分裂箱变，内置和外置CCO各带一个子阵 |
| 首次发生时间 | 2026-09-10 09:30 |
| 影响范围 | 外置CCO下8台逆变器，6台间歇离线 |
| 问题前操作 | 前一天重新导入白名单并重新搜索网络 |
| 关联单号 | DTSxxxxxxxxxxxx |

## 2. 问题现象

- 用户看到的现象：外置CCO下逆变器频繁离线，通信时好时坏。
- 告警：Logger上报“南向设备通信异常”，但不是每次丢包升高都产生告警。
- 日志：`/log/sys_log/logger_run_log.log` 中 `fail_addr` 持续增加。
- 指标：5分钟内 `fail_addr` 从120增加到486；相同STA的100包测试OkRate为82%。
- 发生规律：持续存在，重新登录WEB和刷新页面不恢复。

关键日志示例：

```text
2026-09-10 09:35:00 ... fail_addr=120 ...
2026-09-10 09:40:00 ... fail_addr=486 ...
```

## 3. 定位过程和关键证据

| 检查内容 | 观察结果 | 支持/排除的判断 |
|---|---|---|
| 白名单对应关系 | 内外置CCO白名单与子阵对应正确 | 暂时排除白名单配反 |
| 物理链路 | 相序、开关和接地检查正常 | 暂时排除明显物理问题 |
| 当前频段 | 外置CCO为Band 1 | 记录修改前基线 |
| 同站点对比 | 内置CCO使用Band 2且通信正常 | 支持频段相关判断 |
| 修改后测试 | Band 2下OkRate为98% | 确认频段是本次主要影响因素 |

## 4. 根因结论

- 根因状态：已确认。
- 根因：外置CCO当前使用的Band 1不适合该子阵现场信道环境。
- 机理：该频段下干扰较大，导致报文失败和设备间歇离线。
- 确认依据：相同测试对象和测试参数下，Band 1时OkRate为82%，Band 2时提高到98%，且后续异常指标恢复。
- 适用范围：只确认本次站点和当前软硬件版本；不能推断所有站点都应配置Band 2。

## 5. 实际修复动作

### 动作1：修改外置CCO频段

- 操作对象：外置CCO频段配置对象。注意不是告警上报的Logger设备。
- 操作入口：数采WEB > 设备监控 > MBUS(COMX-249) > 组网配置 > 网络频段。
- 修改前：Band 1。
- 修改内容：选择Band 2；对应接口写入值为3。
- 修改后：Band 2。
- 附加动作：修改完成后执行“重新搜索网络”。
- 生效等待：等待约10分钟，使设备重新组网并积累稳定通信数据。
- 风险和影响：重新搜索期间逆变器会短时离线。
- 权限要求：需要站点维护权限；执行前需要确认允许短时通信中断。

## 6. 验证结果

### 6.1 动作是否生效

- 验证方式：修改后重新查询频段配置。
- 预期结果：返回接口值3，对应Band 2。
- 实际结果：读回值为3。
- 结论：参数修改成功。

### 6.2 原问题是否恢复

- 验证来源：OFDM测试指标、日志指标和活动告警。
- 验证对象和范围：同一外置CCO及同一目标STA。
- 等待和观察时间：重新组网10分钟；之后观察6分钟。
- 成功标准：100包测试OkRate不低于95%；`fail_addr` 不再持续快速增加；目标通信异常不再出现。
- 实际结果：OkRate为98%；连续观察期间 `fail_addr` 增量恢复到正常范围；目标活动告警未再出现。
- 结论：本次问题已恢复。

## 7. 失败处理、限制和回滚

- 不适用情况：无法确认参数目标设备、当前频段无法读取或设备版本不支持目标频段。
- 修改失败时：保留原Band，不继续重复写入。
- 结果不明时：重新只读查询实际频段；未确认前不写入下一个候选。
- 回滚方法：如果Band 2下通信进一步恶化，恢复修改前Band 1并重新搜索网络。
- 必须停止的条件：所有支持频段均无改善、日志停止更新、参数读回与目标不一致。
- 人工/研发介入：需要进一步检查信噪比、物理链路或版本缺陷时转现场/研发。

## 9. 常见不合格写法及修改方式

| 不合格写法 | 问题 | 推荐写法 |
|---|---|---|
| “查看日志是否异常” | 没有文件、关键词和判据 | 写明日志路径、关键词、代表行和正常/异常标准 |
| “调整参数” | 不知道对象和值 | 写明对象、参数名、修改前后值和操作入口 |
| “升级到最新版本” | 目标不可追溯 | 写明问题版本、首个修复版本和升级后验证 |
| “观察一段时间” | 无法形成验证规则 | 写明等待时间、检查次数和成功阈值 |
| “命令执行成功，问题解决” | 混淆动作与问题结果 | 分别记录读回结果和问题恢复证据 |
| “可能是频段问题” | 缺少证据状态 | 标记高度怀疑，并列出已有证据和缺失证据 |
| “失败后重试” | 可能重复副作用 | 说明是否可重试；结果不明时先只读核实 |
| “联系研发” | 没有交接信息 | 写明触发条件和需要携带的日志、版本、已执行动作 |
