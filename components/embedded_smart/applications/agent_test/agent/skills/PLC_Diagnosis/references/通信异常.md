# P001：通信异常

本文件存放通信异常的原因分析、修复动作和准确执行流。由 [SKILL.md](../SKILL.md) 在识别到通信异常类问题后调度读取；通用命令、结果解析和最终总结格式以入口文档为准。

当前仅实现C001网络频段不匹配，作为待验证原因，不代表已经证实根因。其他通信异常原因后续在本文件扩展。

### 输入、识别条件与设备映射

用户描述可能包括通信失败、通信异常、通信中断、离线。描述用于选择P001，实际是否进入修复由当前活动告警决定。

识别归一化活动告警中的 `almname/faultDesc/reason/reasonum/topCauses[].reason/topCauses[].repair/position/locationInfo`，例如“通信异常/通讯异常/通信中断/通信失败”、`communication anomaly/failure/fault`、`communication is abnormal`。优先使用告警名称、具体故障描述和当前告警对应的Top原因/办法，不把设备名称含“通信”、无关告警中的通用说明当作命中。原始 `description/subReasonList` 已被脚本过滤，不会发送给LLM，也不得把它们当作可用判据。

执行时保留以下上下文，贯穿所有步骤：

| 上下文字段 | 内容 |
|---|---|
| `alarm_before` | 命中的原始活动告警；保留seqno、almid、equipid、equipname、reason、position、faultDesc |
| `repair_target` | 频段配置设备ID和类型ID，与告警上报设备分开记录 |
| `band_before` / `band_target` / `band_after` | 修复前、计划目标、读回Band编号及接口值 |
| `failed_bands` / `attempted_bands` | 本次告警处理中已确认失败、已写入尝试的Band集合 |
| `alarm_check_round` | 当前候选Band下的告警解除复查次数，1至6 |
| `parameter_result` | 参数验证：成功/失败/未知/未执行 |
| `problem_result` | 问题复查：本次复查已消除/仍存在/未知/未发现问题 |

本测试环境的频段配置目标为 `equip-id=4099, equip-type-id=33036`；Logger(Local)的告警上报ID为1、类型33028，ESS(Net.8.1)为4101。不要将告警equipid=1直接用于频段修改。用户指定其他站点或设备时先确定对应映射，不能沿用本测试环境映射。若目标映射不明确，停止修复并说明缺少目标设备信息。

### C001：网络频段不匹配

当前修复策略：读取实时频段，将Band 1至5中尚未确认失败的频段按编号升序作为候选，逐个显式写入、读回验证并按间隔复查告警。修复前告警在当前Band已存在，因此当前Band直接记入 `failed_bands`，不重复写入；任一候选下告警解除即结束遍历。

| Band | 接口写入值 | 候选规则 |
|---|---|---|
| 1 | 1 | 未失败且未尝试时可选 |
| 2 | 3 | 未失败且未尝试时可选 |
| 3 | 23 | 未失败且未尝试时可选 |
| 4 | 7 | 未失败且未尝试时可选 |
| 5 | 13 | 未失败且未尝试时可选 |

接口值不是Band编号，必须按上表映射。遍历每个候选时都使用 `set_freq_band --value <接口值>`，不使用默认“当前Band+1”规则。当前Band未知或缺少信号8201时停止并报告未执行修复。`failed_bands` 至少包含修复前当前Band，也包含本次处理中经6次告警复查仍失败的候选；若输入已提供可核验的失败Band证据，也应预先加入并跳过。

### 准确执行流

以下以本测试环境目标4099/33036为例；其他已确定目标替换对应参数。执行完一个步骤后先判断分支，再决定是否执行下一条命令，不把命令块无条件批量运行。

| 步骤 | 执行动作 | 判定与下一步 |
|---|---|---|
| S1 查询并识别问题 | `get_active_alarm --detail-level diagnosis`，查询全部设备 | 查询失败：结束，问题状态未知；无目标通信异常：结束，未发现问题、不修改；命中：保存包含Top原因/建议的alarm_before，进入S2 |
| S2 选择原因和目标 | 选择当前唯一实现分支C001，确定repair_target | 目标不明确：结束并报告缺失信息；明确：进入S3 |
| S3 读取修复前参数 | `get_monitor_info --equip-id 4099 --equip-type-id 33036 --para3 4 --para4 2` | 检查信号8201，保存band_before并加入failed_bands；无有效值：结束、不修改；只有查询授权：报告诊断后结束；可修复：生成Band 1→5中排除failed_bands的升序候选列表，进入S4 |
| S4 写入下一候选 | 按映射执行 `set_freq_band --equip-id 4099 --equip-type-id 33036 --value <候选接口值>` | 调用前将候选加入attempted_bands；main内部重读当前值→写入指定Band→读回。保存 `before/planned/write/after/verification`，进入S5；同一候选的写入命令不重发 |
| S5 验证参数修复 | 解析S4的 `write/after/verification`；即使exec_program退出非0，只要stdout中存在完整JSON也继续解析。仅当 `after=null` 或 `verification.readback_matches=null` 时补一次 `get_monitor_info --equip-id 4099 --equip-type-id 33036` 只读核实 | `success=true`、`exit_code=0`、`write.accepted=true`、`verification.readback_matches=true` 且 `verification.parameter_result="success"`：parameter_result=成功，进入S6；读回明确不是 `planned`或写入明确被拒：parameter_result=失败，将候选加入failed_bands并进入S7；写入结果不明且读回无法确定实际Band：parameter_result=未知，停止后续写入并进入S8 |
| S6 按间隔验证问题 | 每轮执行 `get_active_alarm --detail-level recheck --delay-seconds 60`，查询范围与S1相同，`timeoutMs=90000`；复查结果不包含Top原因/建议，不得覆盖S1的alarm_before；当前候选下最多6轮 | 任一轮目标告警已无：problem_result=本次复查已消除，进入S8；未到6轮且告警仍在：继续S6；6轮后仍在：将该候选加入failed_bands，进入S7；到达上限仍无有效查询结果：problem_result=未知，进入S8 |
| S7 选择后续候选 | 从升序候选列表取下一个不在failed_bands/attempted_bands的Band | 存在候选：重置alarm_check_round并回到S4；已遍历完所有可用Band：problem_result=仍存在，进入S8 |
| S8 形成闭环结论 | 按下方结果矩阵输出报告并结束 | 报告候选顺序、跳过的failed_bands、每次写入/读回和每轮告警复查；不自动回滚 |

S4的main会重新读取当前值：如果 `before` 与S3不同，以S4的 `before` 和 `planned` 作为本次实际修改依据，在报告中说明变化，不继续使用S3中已经过期的目标值。写入结果读取 `write.accepted`，读回值读取 `after`，参数验证读取 `verification.readback_matches/parameter_result`。

S6比较同一设备/故障范围中的通信异常，而非仅比较总告警数或seqno。综合 `equipid/almid/reason/position/faultDesc`：同类故障换了seqno仍视为存在。目标范围出现新的通信异常也不能判定该范围通信恢复。存在多个命中告警时逐条核对；只消除部分则问题仍存在。其他无关告警不影响本问题判断。

每个候选Band都单独使用总入口的「统一告警解除复查规则」：每隔60秒查一次，最多6次。6次内未解除才将该Band判定为本次处理中的失败候选；不得在同一Band的6次复查之间重复写入。

### 双层验证结果矩阵

| 参数修复结果 | 问题修复结果 | 最终结论 |
|---|---|---|
| 成功 | 本次复查已消除 | 本次闭环验证通过：参数已生效，目标通信告警在本次复查中消失；不推断长期稳定性或唯一根因 |
| 成功 | 仍存在 | 参数修复成功，问题尚未解决；C001不足以完成本次修复，停止并报告待扩展原因 |
| 成功 | 未知 | 参数已生效，问题修复结果待确认 |
| 失败或未知 | 本次复查已消除 | 告警已消失，但不能认定本次参数修复成功或将恢复归因于本次操作 |
| 失败或未知 | 仍存在或未知 | 闭环未通过，分别报告参数与问题证据 |
| 未执行 | 未发现问题 | 本次未发现目标通信异常，不修改 |
| 未执行 | 仍存在或未知 | 已发现问题但未能修复，说明停止原因（目标不明、Band5、无权限范围或读取失败等） |

## 执行结束与总结

所有结束分支（包括S1无告警、查询失败、目标不明、Band5、只读诊断、修复失败、验证完成）都必须返回总入口的[最终总结](../SKILL.md#最终总结必做)，输出一份总结后结束。不得仅返回接口JSON或仅说“执行完成”。

总结中同时写明参数修复结果和问题修复结果；记录本问题停在哪一步、实际修改前后值、告警复查证据及后续建议。S7使用上面的双层验证矩阵形成结论；提前结束时，未执行部分明确标注“未执行”。
