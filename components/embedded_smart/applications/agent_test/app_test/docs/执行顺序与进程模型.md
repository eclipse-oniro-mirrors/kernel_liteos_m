# 执行顺序与进程模型

> 回答三个问题：**开机后代码走到哪、静默时程序停在哪、串口输入后又走到哪**；
> 以及三个进程（wifi_wpa / ui_display / app_test）分别在**哪里定义**。
> 宏观架构与二次开发见《架构与二次开发指南.md》，本文聚焦运行期时序。

---

## 1. 三个进程在哪里定义（三层）

| 层 | 作用 | app_test | ui_display | wifi_wpa |
|---|---|---|---|---|
| 编译目标（生成 /bin/xxx） | `executable()` 定义 | `applications/app_test/BUILD.gn:10` | `applications/ui_display_sdk/BUILD.gn:27` | `applications/llm_sdk/BUILD.gn:4`（40 行启动壳，链 `libwpa.so`） |
| 组件注册（编不编进系统） | `vendor/hisilicon/hispark_taurus/config.json` | `:29` | `:28` | 随 `:25` llm_sdk 组件 |
| 开机自启（init 拉起） | `vendor/hisilicon/hispark_taurus/init_configs/init_liteos_a_3516dv300.cfg` | **无服务块，不自启**（调试期串口手动 `exec /bin/app_test`） | **自启**：服务块 `:152-153` + pre-init 段 `:55` `"start ui_display"` | **不在 init.cfg**——是 app_test 的子进程 |

wifi_wpa 的拉起方式：app_test 调 `WifiSvcStart()` 时内部
`fork + exec /bin/wifi_wpa -q -i wlan0 -c <conf>`（见 `llm_sdk/wifi_client.c` 头注释），
app_test 退出后该守护仍在后台。

> 让 app_test 开机自启：照抄 ui_display 的两处写法——在上述 init.cfg 加
> `app_test` 服务块（`"path": ["/bin/app_test"]`）+ 启动列表加 `"start app_test"`，
> 重编 rootfs。语音方案落地时通常需要这一步。

## 2. 开机链路（系统级）

```
U-Boot → 内核 → init(根目录 /etc/init.cfg 概念的来源即上表 init_configs)
        ├─ start foundation / appspawn / media_server / wms_server ... (系统服务)
        ├─ start ui_display      ← 表情进程, 自启即进入自己的主循环
        ├─ start shell           ← 串口 shell
        └─ (wifi_wpa / app_test 不由 init 拉起, 见 §1)
```

## 3. app_test 的 main() 执行序列（app_test.c 约 :130-183，一路同步）

| 步 | 代码 | 行为 | 阻塞性 |
|---|---|---|---|
| 0 | 横幅打印 | 输出 WiFi/LLM/PCA 配置 | 瞬时 |

## 4. 静默期：程序停在哪

主线程**阻塞在 `ConsoleReadline("cmd> ")` 的串口 read 上**（CPU 睡眠）——
这就是静默的本质。此时后台活跃的线程/进程：

| 谁 | 状态 | 在干嘛 |
|---|---|---|
| 主线程 | 睡在串口 read | 等用户输入 |
| WiFi 监视线程 | 周期运行 | 查连通；掉线→重连+触发恢复钩子（正常时安静） |
| 动作队列线程 | **尚不存在** | 懒创建：第一次有动作入队（`EnqueueAct`）才诞生 |
| ui_display 进程 | 独立主循环 | 播当前 GIF + 每 200ms `PollEmojiCmd()` 查表情命令文件 |
| wifi_wpa 守护 | 独立进程 | 关联热点、自动重连 |

## 5. 串口输入后：代码走到哪

```
用户敲命令 + 回车
→ ConsoleReadline 返回一行(主线程从 read 醒来)
→ ShellSplit 拆词 → cmd_find 查命令表(app_test.c g_cmds[], 约 :56)
→ cmd->fn(nv, v)   ← 主线程同步执行命令处理, 以 chat 为例:
     [agent] >> 打印
     BuildPrompt(拼 prompt 字符串, 瞬时)
     LlmSvcChat: WiFi检查 → g_busy 上锁(并发请求返回-99) → WifiMonPause
                 → llm_chat(TCP+TLS握手+HTTP往返, 2~4s, 主线程阻塞在此,
                            期间串口无响应, 敲键无回显属正常)
                 → WifiMonResume → 打印 [llm] 应答/失败 + 回复原文
     ParseReply(逐行解析, 失败→SalvageReply 兜底):
         [SAY]   → 串口打印(瞬时)
         [EMOJI] → SendEmojiCmd 写 /storage/data/emoji_cmd(瞬时)
         [ACT]   → NormalizeAct 参数桥接 → EnqueueAct 入队(瞬时;
                   首次入队在此刻创建动作线程)
→ cmd->fn 返回 → for(;;) 顶部 → 重新打印 "cmd> " 等下一行
```

**主线程回到提示符之后，两件事在后台异步收尾**：

1. **动作线程（ActWorkerLoop）**：队列取动作 → 首次先 `ServoEnsureInit()`
   （I2C 初始化 PCA9685，懒加载）→ `OttoPcaRun` 阻塞执行完一个再取下一个
   （多个 [ACT] 严格按序）。所以提示符回来后机器人还在动，
   此时输入 `stop` 可中止当前动作。
2. **ui_display**：≤200ms 内轮询到 emoji_cmd 文件 → 读一行 → `remove()` →
   切换 GIF（屏幕上会看到 `[ui_display] emoji cmd: xxx`）。

## 6. 线程/进程生命周期速查

| 谁 | 何时创建 | 何时退出 |
|---|---|---|
| 主线程 | main() 进入 | 串口 `quit`（wifi_wpa 守护仍在） |
| WiFi 监视线程 | `WifiSvcMonitorStart()` | 随进程 |
| 动作队列线程 | **首次 EnqueueAct**（懒创建，detached） | 随进程（常驻空转 50ms 轮询队列） |
| wifi_wpa | app_test 内 `WifiSvcStart()` fork+exec | 独立存活，`off`/重连由 wifi_service 管理 |
| ui_display | init.cfg 开机拉起 | 掉了 init 不会自动拉起（需重启或手动 exec） |
| PCA9685 硬件会话 | 首次舵机命令 `ServoEnsureInit()`（懒加载） | 随进程 |

## 7. 时序要点（排查问题时先对照）

1. **开机到 `cmd>` 出现的时间** ≈ 连网(WIFI_CFG_WAIT_SEC 上限) + 两次云端问答
   （各 1~4s）+ 服务拉起；期间敲键无回显属正常（shell 在读）。
2. **`chat` 期间串口无响应**不是死机——主线程阻塞在云端问答；
   超时上限 90s（`LLM_RETRY_BUDGET 18 × 5s`）。
3. **表情比动作先动**是正常的：写文件瞬时、200ms 内被 ui_display 消费；
   动作要等 PCA 初始化（首次）+ 排队执行。
4. **动作"完成(已归位)"但没动**：先查参数是否落在 `steps` 上
   （`NormalizeAct` 桥接是否生效，排队日志会带参数）。
5. **开机不自启 app_test**：`exec /bin/app_test` 手动跑；要自启见 §1 的
   init.cfg 改法。
