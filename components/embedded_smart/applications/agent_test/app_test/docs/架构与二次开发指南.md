## 1. 系统总览

两个独立进程，表情命令经**文件通道**跨进程传递：

```
┌─ 进程1: app_test (串口控制台 + LLM 智能体 + 舵机) ─────────────────────┐
│                                                                        │
│  串口输入 ──> 命令表(app_test.c) ──> AgentCmdChat/ChatU                │
│      │                                   │ (text, UTF-8)               │
│      │                                   v                              │
│      │                        AgentSvcChat(text)      [agent_service.c] │
│      │                        1. BuildPrompt(能力表+模板+示例+文字)    │
│      │                        2. LlmSvcChat ──────> llm_chat(libllmclient.a)
│      │                              │            TLS直连网关(4KB上限,   │
│      │                              │             temperature 0.2)      │
│      │                        3. ParseReply(四行模板解析)               │
│      │                           │    └失败→ SalvageReply(漂移兜底)     │
│      │            ┌──────────────┼──────────────┐                       │
│      │        [SAY]打印      [EMOJI]写文件    [ACT]入队                  │
│      │                        │                  │                       │
│  串口直控 ──> servo_service(run/  │          ActWorkerLoop(后台线程)    │
│  run/post/stop/angle...  post/stop) │          逐个阻塞 OttoPcaRun ──> PCA9685
│                                     v                              │
│                    /storage/data/emoji_cmd(一行表情名,写后即删)      │
└────────────────────────────────────┬───────────────────────────────────┘
                                     v
┌─ 进程2: ui_display (自启, 屏幕表情) ──────────────────────────────────┐
│  主循环每 20 tick(约200ms) PollEmojiCmd(): 读到命令→remove()→切 GIF   │
│  板载按键 key1/key2 = 上/下一个表情(已在 ui_display 侧接管)           │
└───────────────────────────────────────────────────────────────────────┘
```

要点：
- **能力表是唯一来源**（agent_service.c 顶部 `g_emojiTable`/`g_actTable`），
  既拼 prompt 又做回复校验；改能力只动这两张表 + 同步《能力清单与LLM协议.md》。
- **网关是无状态的**（实测：跨连接零记忆，多轮上下文必须在同一条请求内带全），
  所以能力清单+格式约束**每次请求都要随行**（固定部分约 2097B，见 §6.2 的说明）。
- 启动时的 `AgentSvcAnnounce()`（能力上报）只是问候性质，不承担"让模型记住"的职责。

## 3. 启动顺序（app_test.c main，约 :150 起）

1. 控制台初始化，注册命令表（`chat/chatu/ask/uni/scan/pinit/run/post/stop/off/list/key/...`）
2. `WifiSvcStart()` → 失败可串口 `apx <名> <密码>` 重配
3. `WifiSvcSetRecoverHook(LlmSvcGreet)` —— WiFi 恢复后自动重新问候
4. `LlmSvcGreet()` 开机问候（纯 LLM 连通性检查，无格式约束）
5. `AgentSvcAnnounce()` —— 能力清单上报（失败不致命，对话仍带全量能力）
6. `WifiSvcMonitorStart()` —— 断线监视开始（聊天期间自动暂停/恢复）
7. `VoiceSvcStart()` —— 语音唤醒循环后台自启（v4.3；喊 "Luna" 进对话，
   云端 FC 指令经 agent_service 分发；WiFi 未连时唤醒仍监听，联网自动可用；
   `voice stop` 可停，设备不反初始化，`voice start` 秒启）
8. ui_display 由 init.cfg 作为独立服务自启（出厂配置见交付包文档）

## 4. 核心链路

### 4.1 对话链路（chat 一条指令的生命周期）

```
串口行 → AgentCmdChat(拼参数成 UTF-8 句子)
       → AgentSvcChat(text)
           BuildPrompt: [模板] + [能力-表情 21] + [能力-动作 23] + 核心规则
                        + 3个示例 + "用户说: <text>"        (固定部分 2097B)
           LlmSvcChat: 截断自查(>4096 告警) → WifiMonPause → llm_chat
           llm_chat:   json_escape → HTTP/1.0 POST /v1/chat/completions
                       (SNI=VHOST, Bearer=KEY, temperature 0.2, 单 user 消息)
                       → 读响应到 EORF/对端关闭 → extract_content 取正文
           ParseReply: 逐行找 [SAY]/[EMOJI]/[ACT]/[END]
                       (大小写/全角【】:：引号/markdown 装饰容错, 缺行审计)
             [SAY]   → 串口打印
             [EMOJI] → 校验表情名 → SendEmojiCmd 写 /storage/data/emoji_cmd
             [ACT]   → 校验动作名 → NormalizeAct 参数桥接 → EnqueueAct
             无任何标记 → SalvageReply 兜底(expression/表情:/动作:/想法: 等)
           WifiMonResume, 返回回复长度
```

### 4.2 动作队列（agent_service.c）

- 环形队列 `g_actQ[8]`，后台 pthread（懒创建、detached）逐个**阻塞**执行
  `OttoPcaRun(name, par, npar)`；空闲 50ms 轮询
- 返回值语义：0=完成(已归位) / -1=被中止(stop) / 其它=异常
- `NormalizeAct`：模型按规则写 `turn -1`/`walk -1`（±1=方向），而底层签名
  `turn <steps> <periodMs> <dir> <arm>` 参数从左填——这里把首参 ±1 识别为方向，
  展开成 `4 1000 ±1`。**若改了 prompt 的参数约定，必须同步改这里**。

### 4.3 跨进程表情通道（app_test → ui_display）

- 写方：`fopen("w")` 写一行表情名后 `fclose`（覆盖式，≤23 字节）
- 读方：ui_display 主循环 200ms 轮询，读到即 `remove()`（消费即焚）
- 未知名由 ui_display 忽略并打日志；表情文件在 `/storage/data/emoji/<名>.gif`

### 4.4 串口直控（绕过 LLM）

`run/post` 直接执行动作（名字校验同能力表+受控动作），`stop` 中止当前动作，
`angle/us` 单舵机，`trim` 微调——用于调试与演示，与智能体共用底层 otto_pca。

## 6. 二次开发指南

### 6.1 串口输入 → 麦克风语音（v4.3 已实现，本节是设计记录）

**已实现为 `service/voice_service.c/.h`（状态机）+ `service/voice_dialog.c`（执行体）**，
与当初设计一致的地方：
- 语义入口仍是 `agent_service` 的能力表/校验/分发（表情文件通道、动作队列
  原样复用，语音与串口 `chat` 同一规则），新增 `AgentSvcDispatchEmoji/Act`
  两个导出接口供语音层调用
- 串口 `chat` 命令保留作调试后门（deepseek 文字链路独立于语音链路）
- 并发：动作队列已加生产者互斥（串口 + 语音 FC 两个生产者）

与原设想的差异（最终实现走阿里云实时语音，不做"端侧 ASR→文字"）：
- 语音输入不转文字再问 LLM，而是 16kHz PCM 直接上传 **Qwen-Audio-Realtime**
  （WebSocket，`wake_sdk/wake_ws.c`），云端 TTS 音频流回本地播放
- 云端指令不是解析四行文本，而是 **Function Calling**：工具枚举由能力表生成
  （`BuildSessionJson`，单一来源），模型点名真名动作/表情 →
  `AgentSvcDispatchAct/Emoji` 校验分发
- 麦克风/喇叭/唤醒词全部复用 wake_sdk 的 `wake_audio_core`
  （BUILD.gn dep `//applications/wake_sdk:wake_audio_core`，源清单单份维护），
  麦克风独占：与 `my_wake` 程序二选一运行

### 6.2 LLM 网关 → 自有 agent

**先分清两层**：`llm_service.c`（板内封装：互斥/日志/WiFi 联动）和
`libllmclient.a`（传输：TLS/HTTP/JSON）。自有 agent 的接入按兼容程度选路径：

**路径 A：自有 agent 提供 OpenAI 兼容 `/v1/chat/completions`（推荐）**
- 只改 `llm_service.h` 的 `LLM_CFG_IP/VHOST/PORT/KEY/MODEL`，重编即可
- 板子只发**单条 user 消息**（能力+格式+用户文字拼在一条里，≤4KB）；
  若你的 agent 需要区分 system/user，需要走路径 B 扩展 messages 数组
  （现网关已验证接受多轮 messages 数组，llm_client.c 的 body 构造处可扩展）

**路径 B：完全自有协议/传输**
- 按 `llm_client.h` 的契约重新实现 `llm_chat()`：
  `int llm_chat(const llm_gateway_t *gw, const char *message, char *out, int out_len)`
  —— 无状态单轮、message 为 UTF-8（≤LLM_MSG_MAX，超长自截）、out 收正文、
  返回 ≥0 长度或负数错误码（`LLM_ERR_*`，llm_service 按这些码打日志）
- 然后重编 `libllmclient.a` 并**清 obj 重链**（见 §7 坑1）；
  或者干脆绕开该库，把 `LlmSvcChat` 改成调你自己的传输函数
- 若你的 agent 平台侧已经内置了能力表/格式约束（比如 agent 服务端就有
  本机器人的能力档案），`BuildPrompt` 可以瘦身为只发用户文字——
  但**解析端（ParseReply/表校验）必须保留**，本地校验是最后一道防线
- 若 agent 需要**多轮记忆**：现在的链路是无状态单轮，需要
  ① llm_client 支持messages 数组（传输层改动）② service 层维护历史环形缓冲
  （建议保留最近 N 轮，注意 4KB 上限，历史要压缩/截断）

**无状态约束（实测结论，勿绕过）**：该网关跨连接零记忆
（T1"我叫小明"→"收到"，T2 新连接问名字→"不知道"），能力清单**不能只发一次**。
若你的自有 agent 是有状态会话服务，才可以做"首次发能力、后续只发增量"，
届时把 `BuildPrompt` 拆成 `BuildCapPrompt()`（首连一次）+ 用户文字（后续）。

### 6.3 修改回复指令格式

解析完全隔离在 `agent_service.c`，替换点：

| 现格式元素 | 代码位置 | 换格式时 |
|---|---|---|
| 四行模板文案 | `BuildPrompt`（模板+示例段） | 换成你的格式说明与示例 |
| 行标记匹配 `[SAY]/[EMOJI]/[ACT]/[END]` | `TagContent`（大小写/全角【】容错） | 换成新格式的标记/JSON 键匹配 |
| 参数解析 `turn -1` / `walk 2 800` | `ParseActLine`（整数参数） | 按新参数约定重写 |
| 内容清洗（冒号/引号/装饰） | `ContentTrim`/`LineTrim`/`SalvTrim` | 可整体保留，通用 |
| 分发三件套 | `[SAY]`打印 / `SendEmojiCmd` / `EnqueueAct` | **保留不动**（下游通道不变） |
| 参数桥接 ±1=方向 | `NormalizeAct` | 参数约定变了就同步改 |
| 漂移兜底 | `SalvageReply` | 按新格式改字段名（中英文前缀都认） |
| 缺行/未知名审计 | `ParseReply` 尾部 | 保留，定位问题全靠它 |

无论格式怎么改，建议保住三条原则：
1. **无操作也要有显式空值**（现在的 `none`），否则"模型没给"和"不想动"分不清
2. **本地校验名字合法**（`EmojiValid`/`ActFind`）后才分发，非法打日志不执行
3. **换格式先改文档**《能力清单与LLM协议.md》§2，再动代码，两处必须同步

## 7. 已知坑与经验（血泪清单）

1. **预编译库陷阱（最重要的坑）**：app_test 链接的是 `llm_sdk/libllmclient.a`，
   改 `llm_client.c` **不重编库等于没改**。正确流程：
   ```bash
   cd /code/3516/applications/llm_sdk
   CLANG=../..../prebuilts/clang/ohos/linux-x86_64/llvm/bin/clang   # 全路径见 build_llmclient.sh
   $CLANG --target=arm-liteos-eabi -mcpu=cortex-a7 -mfloat-abi=softfp -mfpu=neon-vfpv4 \
          -O2 --sysroot=../../out/hispark_taurus/ipcamera_hispark_taurus/sysroot \
          -I. -I../../third_party/mbedtls/include -fPIC -c llm_client.c -o llm_client.o
   llvm-ar rcs libllmclient.a llm_client.o
   # 然后清 obj 强制重链再整体编译:
   rm -rf ../../out/hispark_taurus/ipcamera_hispark_taurus/obj/applications/app_test
   ```
   （`build_llmclient.sh` 里写的历史路径 `cap_test/` 已不存在，以本流程为准；
   旧库备份为 `libllmclient.a.bak`。）

2. **网关无状态**：能力表必须每请求随行（§6.2 有实测证据）。

3. **消息 4KB 上限**：`LLM_MSG_MAX=4096`，超长截断会在串口打
   `[llm] !! 消息 N 字节超发送上限` 告警。prompt 固定部分 2097B，
   用户文字留约 2KB。

4. **弱模型的格式服从要三层防护**：模板前置的 prompt + temperature 0.2 +
   解析兜底（SalvageReply），缺一层都可能"格式对内容错"或直接漂移。
   串口若出现 `[llm] 线上发送/线上收到` 两行（LLM_WIRE_DEBUG），是定位
   网关问题的铁证——发送字节数、尾部是否完整、HTTP 状态一眼可见。

5. **全角字符容错**：模型会输出全角【】：、中文引号、markdown 装饰，
   解析端已全部兼容；新解析器建议保留这类容错。

6. **能力描述=语义精度**：`handwave(原地挥手(脚不动))` vs
   `greeting(转身挥手打招呼(会转身体))` 的区分直接决定模型选哪个动作
   （六足上 greeting 靠脚枢轴转身，曾被认为是"乱走路"）。改描述文案时
   保持"物理行为可区分"的写法。

7. **参数从左填**：`OttoPcaRun` 参数按位置补默认值，裸 `±1` 会落在
   第一个参数上（turn 的 steps），`NormalizeAct` 桥接层不可删。

8. **printf 64 位陷阱**：`time_t` 等 64 位值进 printf 必须强转
   `(long)`，否则 varargs 错位读（wifi_service.c 有注释）。

9. **聊天期间 WiFi 监视要暂停**：`LlmSvcChat` 里 `WifiSvcMonPause/Resume`
   是为防监视流量干扰长连接，换传输层时保留该机制。

10. **表情通道是覆盖写**：`fopen("w")` 单写者假设；多写者（语音+串口同时
    切表情）以最后一次为准，ui_display 读后即删，无需去重。

## 9. 换板复现指南（拿到 applications 文件夹后的一次性配置）

> 场景：别人拿到你整个 `applications/` 文件夹，放到他自己的
> OpenHarmony 小型系统（liteos-a）源码树上，把"表情+LLM 智能体+舵机"
> 功能跑起来。以下按一次性配置顺序写。

### 9.1 前提与适用范围

- 目标树是可完整编译的 OpenHarmony liteos-a 小系统（本功能在
  Hi3516DV300/hispark_taurus 上开发验证；同 SoC = 纯配置即可，异 SoC 见 9.8）
- 拿到的内容 = `applications/` 下五个组件：
  `llm_sdk`（WiFi/LLM 传输库）、`pca9685_sdk`（舵机）、`key_sdk`（按键 HDF）、
  `ui_display_sdk`（屏幕表情）、`app_test`（控制台+智能体），
  **外加表情资产目录 `vendor/hisilicon/hispark_taurus/data/emoji/`**
  （21 个 240x240 GIF，缺它表情显示不出来，见 9.2 第 3 步）
- 组件里的 `lib*.a/.so` 是 **arm-liteos-eabi 预编译产物**：同工具链直接用；
  异工具链按 §7 坑1 的流程重编（各 SDK 目录自带 build_*.sh）

### 9.2 放代码 + 注册组件（必做，3 步）

1. 五个组件目录整体拷进 `<你的树>/applications/`（同名合并覆盖）
2. 在 `<树>/vendor/<厂商>/<产品>/config.json` 的产品 components 里注册
   （本仓库参考 `vendor/hisilicon/hispark_taurus/config.json:25-29`）：
   ```json
   { "component": "llm_sdk", "features":[] },
   { "component": "pca9685_sdk", "features":[] },
   { "component": "key_sdk", "features":[] },
   { "component": "ui_display_sdk", "features":[] },
   { "component": "app_test", "features":[] }
   ```
3. **表情 GIF 资产拷进产品 vendor 数据目录**：把
   `vendor/hisilicon/hispark_taurus/data/emoji/`（21 个 240x240 GIF）整体拷到
   `<你的树>/vendor/<厂商>/<产品>/data/emoji/`。这是表情资源的源头
   （打包链路：BUILD.gn `copy("emoji_assets")` → out 的 `data/emoji/` →
   fs.yml userfs 段 `source_dir: data`（fs.yml:185）→ 板上 `/storage/data/emoji/`）。
   **漏了这步板上没有任何 GIF**，`chat 换个开心的表情` 只会在串口打
   `[emoji] load failed: /storage/data/emoji/xxx.gif`，屏幕表情永远出不来。
   注：`ui_display_sdk/assets/emoji/` 是同一套 GIF 的镜像（当前 BUILD.gn
   相对路径引用的就是它），两处必须保持一致——增删表情时两边同步更新，
   详见 ui_display_sdk/docs/静态资源全链路指南_以emoji为例.md

### 9.3 第三方依赖确认（缺了编不过）

| 依赖 | 用途 | 缺失后果 |
|---|---|---|
| `third_party/mbedtls`（含 `mbedtls_shared` 目标） | LLM 的 TLS | app_test/llm_ask 链接失败 |
| `third_party/wpa_supplicant`（2.9_standard，产 libwpa.so） | wifi_wpa 守护 | WiFi 全链路不可用 |
| HDF platform（I2C/GPIO manager 服务） | 舵机 I2C、按键 | `scan`/`pinit` 报 HDF 错 |
| 显示栈（framebuffer/媒体库） | ui_display 播 GIF | 链接失败或黑屏 |

### 9.4 一次性配置改点（按你的环境改 5 处头文件）

| 文件 | 宏 | 说明 |
|---|---|---|
| `app_test/service/wifi_service.h:12-14` | `WIFI_CFG_SSID/PSK/WAIT_SEC` | 空串=启动跳过连网 |
| `app_test/service/llm_service.h:12-16` | `LLM_CFG_IP/VHOST/PORT/KEY/MODEL` | 换成你自己的网关与 key |
| `app_test/service/servo_service.h:12-13` | `SERVO_CFG_BUS/ADDR` | I2C 总线号与 PCA9685 地址 |
| `app_test/service/agent_service.c` 顶部 | `g_emojiTable`/`g_actTable` | 换成你机器人的能力（描述即语义，见 §7 坑6） |
| `ui_display_sdk/ui_display.cpp:55` | `EMOJI_CMD_FILE` | 与 agent_service.h 保持一致 |

### 9.5 硬件与接线清单（本仓库的参考接法）

- **PCA9685**：I2C6（Hi3516 上 Y18=GPIO3_2=SCL、AA18=GPIO3_3=SDA）、
  7 位地址 0x40（地址跳线全开）；**舵机独立供电，且必须与板子共地**
  （pca9685.h:19-22 有接线图）
- **按键**：key1=GPIO0_2、key2=GPIO0_1（ui_display 侧消费，切表情）
- **屏**：表情 GIF 240x240（源头在 `vendor/hisilicon/hispark_taurus/data/emoji/`，
  由 BUILD.gn 的 `emoji_assets` copy 目标打进 userfs data 分区，板上
  `/storage/data/emoji/<名>.gif`；换板时按 9.2 第 3 步一并拷走）

### 9.6 编译、烧录、首次上电

1. `python3 build.py <你的产品名>`（本仓库 `ipcamera_hispark_taurus`）
2. 烧 `rootfs_vfat.img / userfs_vfat.img / OHOS_Image.bin`（HiTool 网口烧录，
   见仓库根《Hi3516外设配置与烧录指南.md》）
3. 首次上电串口：`ip` 查看联网 → 未连则 `apx <热点> <密码>` →
   `exec /bin/app_test`（或按 §1 给 init.cfg 加自启）→ `help` 确认命令表
4. 舵机：`scan 6` 确认 0x40 应答 → `pinit` → `list` → `run walk`

### 9.7 复现验收

跑 §8 的用例集（`chat 换个开心的表情` 只切表情、复合指令、`stop` 中止、
`[llm] 线上发送 ~2300B` 无截断……全部通过即复现完成）。

### 9.8 换其它 SoC 的移植点（异板才需要）

| 模块 | 板相关点 | 工作量 |
|---|---|---|
| ui_display | 显示栈/分辨率/GIF 渲染——最大的移植项 | 大 |
| pca9685_sdk | HDF I2C 总线号、引脚（用户态 HDI 接口是通用的） | 小 |
| key_sdk | HDF GPIO 引脚号 | 小 |
| wifi | WiFi 芯片驱动 + wpa_supplicant 适配（llm_sdk 的 wifi_wpa 壳通用） | 中 |
| 预编译库 | 异工具链全部重编（§7 坑1 流程，各 SDK 自带 build 脚本） | 小 |
| app_test/agent | 纯 POSIX C，理论上零改动 | 零 |
